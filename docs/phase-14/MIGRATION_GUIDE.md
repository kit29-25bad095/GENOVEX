## 1. Executive Policy: The Zero-DDL Production Standard

In production and staging environments, executing uncontrolled Data Definition Language (DDL) statements via `Base.metadata.create_all()` is **strictly prohibited**. 

### 1.1 Why `Base.metadata.create_all()` is Blocked in Production
1. **No Migration History:** Does not record executed changes in `alembic_version`.
2. **Destructive Limitations:** Cannot safely modify columns, alter indexes, rename tables, or perform non-destructive schema migrations on live tables.
3. **Locking & Downtime:** Can trigger exclusive table locks without planned maintenance windows.
4. **Environment Divergence:** Causes silent schema drift between developer machines, CI runners, and production databases.

### 1.2 Lifespan Enforcement
In `backend/main.py`, application startup is controlled via the FastAPI lifespan handler:
```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # Only bootstrap SQLite schemas in local development/test environments
    if settings.ENVIRONMENT in ("development", "test") and settings.DATABASE_URL.startswith("sqlite"):
        # Local development bootstrap
        pass
    else:
        # In staging/production (e.g. PostgreSQL), Base.metadata.create_all() is skipped.
        # Schema management is exclusively executed via: alembic upgrade head
        logger.info("Production/Staging mode: Skipping create_all; schema governed by Alembic.")
    yield
```

### 2.2 Reversible Migration Operations
Every migration script must provide complete, symmetrically tested `upgrade()` and `downgrade()` functions.
- `upgrade()`: Executes forward DDL (creating tables, adding indexes, migrating data).
- `downgrade()`: Completely undoes forward DDL in reverse dependency order (dropping indexes, dropping tables), restoring the database to the prior revision without leaving orphaned constraints.

## 3. Migration Operational Commands

All commands are executed from the backend directory or with `backend/alembic.ini` specified.

### 3.1 Applying Migrations (Deployment)
To apply all pending migrations up to the latest revision:
```bash
alembic upgrade head
```

To upgrade to a specific revision:
```bash
alembic upgrade <revision_id>
```

### 3.2 Inspecting Migration Status
To check current database version vs. latest available head:
```bash
alembic current
alembic heads
```

To view chronological migration history:
```bash
alembic history --verbose
```

### 3.3 Verifying Zero Schema Drift
To verify that the current physical database schema exactly matches SQLAlchemy `Base.metadata` with zero discrepancy:
```bash
alembic check
```
If any table, column, index, or constraint differs, `alembic check` immediately raises an error detailing the drift.

## 4. Authoring New Migrations Runbook

When introducing schema modifications in future phases:

### Step 1: Update SQLAlchemy Models
Update or add ORM model definitions inside `backend/app/models/` or `backend/app/core/security.py`.

### Step 2: Generate Migration Script
Generate an autogenerated migration draft:
```bash
alembic revision --autogenerate -m "describe_change"
```

### Step 3: Manual Inspection & Sanitization
Open the newly generated migration file in `backend/alembic/versions/` and inspect both `upgrade()` and `downgrade()`:
- Ensure table names and column types match conventions.
- Verify foreign key cascades and nullability.
- Ensure all indexes have explicit naming conventions.
- Confirm non-destructive defaults for existing rows (e.g. `server_default`).

### Step 4: Verification Cycle
Execute the complete migration lifecycle against an isolated disposable database:
1. `alembic upgrade head`
2. `alembic check`
3. `alembic downgrade -1`
4. `alembic upgrade head`

## 5. Disaster Recovery & Rollback Runbook

### 5.1 Immediate Rollback Procedure
If a migration fails or causes unexpected performance degradation during deployment:
1. Revert to the previous stable revision:
   ```bash
   alembic downgrade -1
   ```
2. Verify system health via the `/health` endpoint:
   ```bash
   curl -s http://127.0.0.1:8000/health
   ```
3. Inspect `audit_logs` for any connection or migration errors.

### 5.2 Database Point-in-Time Recovery (PostgreSQL AWS RDS UAE)
In production on AWS RDS (`me-central-1`):
1. AWS RDS automated daily backups and 5-minute transaction logs provide Point-in-Time Recovery (PITR) up to 35 days.
2. In the event of catastrophic data corruption or human error, restore the DB instance to a target timestamp prior to the failed migration using the AWS Console or CLI:
   ```bash
   aws rds restore-db-instance-to-point-in-time \
       --source-db-instance-identifier genovex-prod-db \
       --target-db-instance-identifier genovex-prod-restored \
       --restore-time "2026-11-21T05:00:00Z" \
       --region me-central-1
   ```
